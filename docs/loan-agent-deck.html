Loan Processing Agent

Multi-agent orchestration with Google ADK on OpenShift AI

Raghu Banda  ·  Red Hat AI

Hey everyone. So today I want to walk you through an agent we built on OpenShift AI — it processes loan applications end-to-end, from reading the paperwork to generating an approval or decline letter. It's built on Google's Agent Development Kit — ADK — and it uses several OpenShift AI platform capabilities along the way: model serving, AutoRAG for regulatory knowledge, MLflow for tracing. The interesting part isn't any one of those things in isolation — it's how they fit together in a real workflow where you need to get the answer right, not just get an answer fast. Let me show you how it works.

Overview

What does this agent actually do?

A user submits a loan application. The agent reads it, checks SBA eligibility rules, calculates pricing, and either generates an approval letter or a compliant decline notice — with a human approving the final decision.

So what does this thing actually do? In plain terms: someone pastes in a loan application — could be text, could be a PDF — and the agent takes it from there. It extracts the structured data, checks whether the business is eligible under SBA rules, calculates an interest rate and monthly payment, and then stops and asks the user: "Here's the pricing, do you want to go ahead?" Only after a human says yes does it generate the approval letter. If the business isn't eligible, it skips pricing entirely and generates a compliant decline notice that meets ECOA regulations. The key numbers: there are 5 agents total — one orchestrator and four specialists. The knowledge base has 9 regulatory documents that the agent retrieves from at decision time. And the whole thing is designed so you can restart the pod, come back the next day, and pick up exactly where you left off.

Architecture

Why multiple agents instead of one big prompt?

Focused prompts

Each agent has one job with its own system prompt and Pydantic output schema. The underwriting agent doesn't know about pricing. The pricing agent doesn't know about decline letters.

Isolated tools

Sub-agents only get the tools they need. The orchestrator can't accidentally call calculate_loan_pricing — only PricingAgent has it. No tool leakage between stages.

Testable boundaries

Each agent writes structured output to a session state key. You can test underwriting in isolation, swap out the pricing logic, or change the decline letter format without touching the other agents.

The orchestrator calls each sub-agent using ADK's AgentTool pattern — they look like regular tool calls to the LLM, but each one spins up a full agent with its own prompt and model context.

So why didn't we just write one big prompt that does everything? We tried that early on, and the problem is that loan processing has genuinely different reasoning modes. Reading a PDF and extracting fields is a different task from checking eligibility rules, which is different from calculating interest rates. When you put all of that in one prompt, the model gets confused about which step it's on, it hallucinates numbers from the wrong stage, and it's really hard to debug. With separate agents, each one has a focused prompt, a specific output schema, and only the tools it needs. The underwriting agent literally cannot call the pricing tool — it doesn't have access to it. And because each agent writes structured output to a session state key, you get clean boundaries. You can test underwriting in isolation by just checking whether the UnderwritingReport looks right for a given application. The way this works in ADK is through the AgentTool pattern — the orchestrator calls each sub-agent as if it were a regular tool, but under the hood ADK spins up a full agent with its own prompt and model context.

Architecture

The four-agent pipeline

Four agents in sequence via ADK AgentTool. Eligible loans go through pricing + HITL approval. Ineligible loans auto-skip pricing and generate a compliant decline letter with regulatory guidance from AutoRAG.

Here's the actual pipeline. Every loan application goes through these four stages in order. First, DocumentExtractionAgent reads the application — it can handle PDFs, images, or plain text because we inject the document into the model context using a before_model callback. It outputs a structured LoanApplicationData object — business name, EIN, revenue, loan amount, all the fields. Then UnderwritingAgent takes over. It calls a mock CRM to check if the business data matches internal records, and then it queries AutoRAG twice — once for SBA eligibility rules that apply to this specific business profile, and once for industry-specific risk and NAICS ineligibility codes. It returns an UnderwritingReport with a status: ELIGIBLE, INELIGIBLE, or REVIEW. If the business is eligible or needs review, PricingAgent runs — it calculates the interest rate based on risk tier, the monthly payment, total interest over the loan term. Then the orchestrator stops and presents the pricing to the user. "Here's what the loan would look like. Do you want to approve?" Only after the user says yes does LoanDecisionAgent generate the formal approval letter. Now, the interesting branch: if the business is ineligible, pricing gets auto-skipped — there's a callback that prevents it from running. The orchestrator loads the adverse-action skill, and LoanDecisionAgent generates a decline letter. Inside that tool call, it automatically queries AutoRAG for ECOA and Regulation B requirements to make sure the decline letter is compliant. That RAG call happens internally — the LLM doesn't see it as a separate tool call.

AutoRAG

Retrieval-augmented regulatory knowledge

How it works
  • OGX vector store with Milvus backend and nomic-embed-text-v1.5 embeddings
  • UnderwritingAgent calls retrieve_underwriting_context — one LLM tool call that internally makes 2 AutoRAG queries: eligibility rules + industry guidance
  • LoanDecisionAgent calls finalize_loan_decision — on the decline path, it internally calls retrieve_regulatory_guidance for ECOA adverse action requirements
  • Each query returns up to 3 chunks — focused retrieval, not a document dump
  • If AutoRAG is down, the agent falls back to a static eligibility_rules.json
The 9-document corpus
  • SBA general eligibility + DSCR requirements
  • Collateral requirements + LTV table
  • Prohibited business types (13 CFR § 120.110)
  • Adverse action notice rules (ECOA / Reg B)
  • Prohibited NAICS codes (30 codes)
  • Industry risk assessment guide
  • Risk tier + rate pricing guide
  • Applicant FAQ (20 Q&A)
  • Reapplication guidance
Let's talk about AutoRAG, because this is one of the more interesting design decisions. The agent needs to make regulatory decisions — is this business eligible under SBA rules? What NAICS codes are prohibited? What does ECOA require in a decline letter? We could have fine-tuned a model or stuffed all of this into the system prompt, but regulatory rules change, and you want to be able to update them without retraining or redeploying. So we have a 9-document corpus seeded into an OGX vector store — that's RHOAI's AutoRAG service, backed by Milvus with nomic-embed-text-v1.5 for embeddings. The agent hits it in two places. During underwriting, the LLM calls a tool called retrieve_underwriting_context. From the LLM's perspective, that's one tool call. But internally, that tool makes two separate AutoRAG queries — one for SBA eligibility rules matching this specific application profile, and one for industry-specific risk and NAICS ineligibility. Each query returns up to 3 chunks. Then on the decline path, when finalize_loan_decision runs, it automatically queries AutoRAG for ECOA and Regulation B requirements — the LLM doesn't even see this as a separate tool call, it happens inside the tool. And there's a fallback: if AutoRAG isn't configured or isn't reachable, the underwriting agent falls back to a static JSON file with the eligibility rules. The agent doesn't crash — it just works with less context.

Safety

Callbacks — guardrails at every lifecycle point

HookCallbackWhat it actually does
before_agent extract_request_id Parses the loan ID (SBL-YYYY-XXXXX) from the user message. No ID? Agent asks for one instead of guessing.
before_tool halt/skip guard Blocks tool execution if the process is halted, completed, or if pricing should be skipped for ineligible loans.
before_model inject_document Injects the loan application PDF or image into the LLM request context — only for DocumentExtractionAgent.
after_agent state_logging Persists every sub-agent's structured output to SQLite. Detects INELIGIBLE status and flags PricingAgent for skip.
after_agent llm_judge_gate A second LLM call that checks trajectory, grounding, and completeness. If it fails, the response is blocked.

The LLM-as-Judge validates every orchestrator response: Did the tools run in the right order? Do all numbers match the structured outputs? Is anything missing? If any check fails, the user sees a generic retry message — not a hallucinated answer.

This is where the guardrails live, and honestly this is probably the most important slide if you're thinking about building something similar. ADK gives you four callback hooks — before_agent, before_tool, before_model, after_agent — and we use all of them. The before_agent callback extracts the loan ID from whatever the user typed. If there's no valid ID, the agent asks for one instead of making something up. The before_tool callback is a gate — it checks whether the current process is halted, already completed, or whether the tool should be skipped. This is how the pricing auto-skip works: when the underwriting agent returns INELIGIBLE, the after_agent callback sets a flag, and the before_tool callback on PricingAgent sees that flag and blocks execution. The before_model callback is used by DocumentExtractionAgent to inject the actual document content into the LLM request. And then the big one: the LLM-as-Judge. After every orchestrator response, a second LLM call runs that checks three things. One, trajectory: did the tools get called in the right order? Two, grounding: do all the numbers in the response actually match the structured agent outputs? No hallucinated interest rates. Three, completeness: is anything missing that should be in the response? If any of those checks fail, the response gets blocked. The user sees a generic "please try again" message instead of wrong information. For a financial application, this is non-negotiable.

Resilience

Repair and resume — surviving failures

Dual-write: every sub-agent writes to both ADK session state and SQLite.

  • Pod restart? check_process_status reloads completed steps from SQLite
  • Missing data? Agent halts, asks the user, resumes from that step
  • User returns hours later? SQLite picks up where things left off
  • Approval in a new session? _load_step_data_from_db() loads prior outputs so the letter can be generated
So one of the realities of running agents on a platform is that pods restart, sessions expire, and users walk away and come back the next day. If your agent loses all its state when that happens, you're asking users to re-submit their loan application from scratch. That's not acceptable. Here's how we handle it. Every time a sub-agent completes, we write its output to two places: ADK's in-memory session state, and a SQLite database on a persistent volume. The first tool the orchestrator calls — every single time — is check_process_status. It looks up the loan ID in SQLite and figures out: is this a new application? A resume? A status check? If it's a resume, it loads all the completed step data back into the new ADK session, and the orchestrator picks up from the next uncompleted step. There's also a more subtle edge case. When the user approves the pricing, that "yes" might arrive in a completely new API session — maybe the pod restarted between the pricing presentation and the user's response. ADK session state would be empty. So inside finalize_loan_decision, there's a fallback function called _load_step_data_from_db that checks each prior agent's output key, and if it's empty, loads it from SQLite. This means the approval letter can always be generated, regardless of session continuity.

Platform

What this looks like on OpenShift AI

Model Serving (MaaS)

Gemini 2.5 Flash via OpenAI-compatible endpoint through LiteLLM. Switch to Vertex AI or direct API key by changing env vars — no code changes.

AutoRAG (OGX)

9-doc regulatory corpus in Milvus + nomic-embed-text-v1.5. Queried 3 times per loan: 2 at underwriting, 1 at loan decision.

MLflow Tracing

Optional — set MLFLOW_TRACKING_URI and every LLM call auto-logs as spans. Degrades gracefully if unavailable.

OK, so let's talk about where the platform fits in, because this agent isn't just running in a notebook somewhere. It's using several RHOAI capabilities as part of its normal operation. First, model serving. The LLM — Gemini 2.5 Flash — is served through RHOAI's model-as-a-service endpoint. The agent talks to it via an OpenAI-compatible API through LiteLLM. Two env vars: MAAS_BASE_URL and MAAS_API_KEY. The nice thing is the code also supports Vertex AI and direct Gemini API keys — you just change the environment variables and the model factory in gemini_custom.py handles the rest. No code changes. Second, AutoRAG. This is RHOAI's managed RAG service built on OGX. We have a Milvus vector store with nomic-embed-text-v1.5 for embeddings, and the 9-document regulatory corpus is seeded using a script that uploads the markdown files to the vector store. The agent queries it three times per loan application — focused queries, three chunks max each. Third, MLflow tracing. This is optional but really useful for debugging. Set MLFLOW_TRACKING_URI and every LLM call automatically gets logged as a span — you can see exactly what prompts went in, what came back, how long each call took. If the MLflow server isn't there, the agent starts fine without it. It does a health check on startup and degrades gracefully. And fourth, the deployment itself. It's a standard FastAPI container running on OpenShift, with a persistent volume for the SQLite state database, ConfigMap for operator-tunable parameters like interest rate tiers and bank branding, and SealedSecrets for the API key. We also use OpenShell for network isolation — the agent can only reach the MaaS gateway and the AutoRAG endpoint, nothing else.

Knowledge

Skills — domain knowledge loaded on demand

The orchestrator loads markdown files as "skills" using ADK's SkillToolset. These aren't hard-coded into prompts — the LLM decides when to load them based on context.

SkillWhen it's loadedWhat it contains
loan-orchestration-protocol Start of every new application Step-by-step HITL workflow: extract → underwrite → price → approve/decline
loan-eligibility-guide When explaining eligibility decisions 5 SBA eligibility rules, risk flags, status definitions
loan-pricing-guide After PricingAgent returns Risk tier table (Tier 1–4), rate ranges, how to present pricing to the user
loan-adverse-action Before generating a decline letter ECOA requirements, decline letter template, tone and compliance guidance

Only the orchestrator has access to skills. Sub-agents are locked down: disallow_transfer_to_parent=True, disallow_transfer_to_peers=True. They can't load skills, can't call other agents, can't transfer control.

One thing that's easy to overlook but actually matters a lot is how domain knowledge gets into the agent. We have two mechanisms: AutoRAG for the regulatory corpus, and skills for workflow knowledge. Skills are just markdown files — loan-orchestration-protocol tells the agent the exact step-by-step workflow it should follow. loan-eligibility-guide has the five SBA eligibility rules. loan-pricing-guide has the risk tier table and how to present pricing to a user. loan-adverse-action has ECOA requirements and a decline letter template. These are loaded via ADK's SkillToolset — the orchestrator has two tools, list_skills and load_skill, and it decides when to load them based on context. When it starts processing a new application, it loads the orchestration protocol. When it needs to generate a decline letter, it loads the adverse-action skill first. The key design decision is that only the orchestrator has access to skills. Sub-agents are completely locked down — disallow_transfer_to_parent is True, disallow_transfer_to_peers is True. They can't load skills, they can't call other agents, they can't transfer control. They do their one job and return structured output.

What a real conversation looks like

User: "Process this loan application for SBL-2026-10001: Acme Bakery, $150K loan, 5 years in business, $420K annual revenue..."

Behind the scenes:

check_process_status → load_skill("loan-orchestration-protocol") → DocumentExtractionAgent → UnderwritingAgent + 2 RAG queries → PricingAgent

Agent: "Application processed. Acme Bakery qualifies as Tier 2 (Moderate Risk). Proposed terms: 7.75% interest rate, $3,012.43/month over 60 months. Total interest: $30,745.80. Do you approve these terms?"

User: "Yes, approve it."

Behind the scenes:

check_process_status (may reload from SQLite) → LoanDecisionAgent → LLM-as-Judge → response

Agent: "Loan SBL-2026-10001 has been approved. Formal approval letter generated (ref: DL-2026-10001). The letter has been sent to the applicant at acme@example.com."

Let me walk through what this looks like in practice. The user pastes in a loan application with the details — business name, loan amount, financials. Behind the scenes, the orchestrator runs check_process_status first, creates a new process in SQLite, loads the orchestration protocol skill, and then runs through the pipeline. DocumentExtractionAgent pulls out the structured fields. UnderwritingAgent checks eligibility — it queries AutoRAG for SBA rules and industry guidance, checks the mock CRM, and comes back with "eligible, Tier 2 moderate risk." PricingAgent calculates the rate — 7.75% for Tier 2, $3,012 a month. Then the orchestrator stops. It presents the pricing and asks: "Do you approve?" This is the HITL pause. The agent doesn't proceed until it gets a yes. Now, here's where the resilience matters. Between the user seeing the pricing and saying "yes," anything could have happened — pod restart, session timeout, the user went to lunch. When "yes" comes in, check_process_status runs again, reloads the completed steps from SQLite, and LoanDecisionAgent generates the approval letter. The LLM-as-Judge validates the final response — are the numbers correct? Is the approval reference there? — and only then does it go to the user.
