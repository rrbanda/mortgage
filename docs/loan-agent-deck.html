Loan Processing Agent

Multi-agent orchestration with Google ADK on OpenShift AI

Raghu Banda  ·  Red Hat AI

So what I'm going to walk you through today is a production-grade multi-agent system that processes loan applications end-to-end. It's built on Google's Agent Development Kit — ADK — running on OpenShift AI, and it's a good reference architecture because it exercises several platform capabilities in a single workflow: MaaS for model serving, AutoRAG backed by OGX and Milvus for regulatory knowledge retrieval, MLflow for distributed tracing, and the OpenShell sandbox for network-level isolation. The reason this is interesting from an architecture standpoint isn't any one of those capabilities in isolation — it's the composition pattern. We're running five LlmAgent instances coordinated through ADK's AgentTool mechanism, with four ADK callback hooks enforcing policy at every lifecycle point, an LLM-as-Judge quality gate that validates every response for trajectory correctness and data grounding, and a SQLite dual-write persistence layer that enables repair and resume across pod restarts and session boundaries. The domain is loan processing — SBA 7(a) loans specifically — which forces you to deal with regulatory compliance, structured output validation, human-in-the-loop approval gates, and the fact that you absolutely cannot hallucinate an interest rate or an eligibility determination. If the agent gets a number wrong, that's a regulatory violation. So every design decision in this system is oriented around correctness, not speed. Let me walk you through how it's put together.

Overview

What does this agent actually do?

A user submits a loan application. The agent reads it, checks SBA eligibility rules, calculates pricing, and either generates an approval letter or a compliant decline notice — with a human approving the final decision.

At the highest level: a user submits a loan application — could be pasted text, could be a PDF, could be an image — and the agent takes it through a four-stage pipeline. Document extraction, underwriting, pricing, and loan decision. But there are three distinct execution paths depending on the underwriting outcome, and the architecture handles all of them differently. Path A is the happy path: business is eligible, pricing runs, the orchestrator presents the terms and pauses for human approval — genuine HITL, not a confirmation dialog — and only after explicit consent does LoanDecisionAgent generate a formal approval letter. Path B is the ineligible path: the UnderwritingAgent returns INELIGIBLE, a callback automatically sets a skip flag for PricingAgent, the orchestrator loads the adverse-action skill for ECOA compliance, and LoanDecisionAgent generates a decline letter grounded in actual Regulation B text retrieved from AutoRAG. Path C is the repair path: DocumentExtractionAgent detects missing critical fields, the process halts, the user provides the missing data, and the agent resumes from exactly where it stopped — no re-running completed stages. The 1+4 architecture: one orchestrator LlmAgent with five tools — a SkillToolset for domain knowledge, check_process_status for state management, and four AgentTool wrappers around the sub-agents. Each sub-agent has its own model context, system prompt, Pydantic output_schema, and isolated tool set. The orchestrator is the only agent with transfer capabilities — sub-agents are locked with disallow_transfer_to_parent and disallow_transfer_to_peers both set to True. The 9-document AutoRAG corpus covers SBA eligibility, DSCR requirements, collateral and LTV tables, prohibited business types under 13 CFR 120.110, prohibited NAICS codes, industry risk assessment, ECOA adverse action requirements, pricing tier guidance, applicant FAQ, and reapplication guidance. About 78KB of source material seeded into Milvus via a one-time seed_autorag.py script using nomic-embed-text-v1.5 embeddings. The resume capability is backed by ProcessStateService — a SQLite-based persistence layer on a PVC at /app/data/. Every sub-agent completion writes to both ADK in-memory session state and SQLite. check_process_status is always the first tool call in any turn — it looks up the loan ID, determines the action (proceed, resume, return_status), and reloads completed step data into the fresh ADK session if needed.

Architecture

Why multiple agents instead of one big prompt?

Focused prompts

Each agent has one job with its own system prompt and Pydantic output schema. The underwriting agent doesn't know about pricing. The pricing agent doesn't know about decline letters.

Isolated tools

Sub-agents only get the tools they need. The orchestrator can't accidentally call calculate_loan_pricing — only PricingAgent has it. No tool leakage between stages.

Testable boundaries

Each agent writes structured output to a session state key. You can test underwriting in isolation, swap out the pricing logic, or change the decline letter format without touching the other agents.

The orchestrator calls each sub-agent using ADK's AgentTool pattern — they look like regular tool calls to the LLM, but each one spins up a full agent with its own prompt and model context.

The single-agent approach was our first attempt, and it fell apart for three concrete reasons. First, prompt interference — when you put document extraction instructions, underwriting rules, pricing calculations, and letter generation templates in one system prompt, the model starts mixing reasoning modes. We saw it pull field values from the wrong stage, apply pricing logic during underwriting, and hallucinate interest rates before PricingAgent even ran. Second, tool sprawl — a single agent with all eight tools (check_process_status, get_internal_business_data, retrieve_underwriting_context, calculate_loan_pricing, finalize_loan_decision, list_skills, load_skill, load_skill_resource) makes unpredictable tool choices. Third, testability — you can't unit-test underwriting logic if it's entangled with pricing and decision generation. The ADK AgentTool pattern solves this cleanly. In agent.py, the root_agent is an LlmAgent with five tools: SkillToolset, check_process_status as a standalone function tool, and four AgentTool wrappers — AgentTool(document_extraction_agent), AgentTool(underwriting_agent), AgentTool(pricing_agent), AgentTool(loan_decision_agent). From the orchestrator LLM's perspective, calling "DocumentExtractionAgent" is just a tool call with arguments. But ADK spins up a full LlmAgent with its own system prompt, model context, and output_schema. The sub-agent runs to completion, returns structured output, and ADK writes it to session state under the agent's output_key — for example, "DocumentExtractionAgent_output". The tool isolation is explicit. UnderwritingAgent's tools list is exactly two items: get_internal_business_data (mock CRM lookup) and retrieve_underwriting_context (the AutoRAG wrapper). PricingAgent has one tool: calculate_loan_pricing. LoanDecisionAgent has one: finalize_loan_decision. None of them have access to each other's tools, to SkillToolset, or to check_process_status. And they're locked down with disallow_transfer_to_parent=True and disallow_transfer_to_peers=True — they can't autonomously decide to call another agent or hand control back. Each sub-agent also has a Pydantic output_schema — LoanApplicationData, UnderwritingReport, PricingResult, LoanDecisionResult. ADK enforces structured output, so the LLM is constrained to return valid JSON that matches the schema. This is what makes the grounding check in the LLM-as-Judge possible — you can compare the orchestrator's natural language response against the structured agent outputs field by field.

Architecture

The four-agent pipeline

Four agents in sequence via ADK AgentTool. Eligible loans go through pricing + HITL approval. Ineligible loans auto-skip pricing and generate a compliant decline letter with regulatory guidance from AutoRAG.

Let me walk through the diagram in detail, because the execution flow is more nuanced than "four agents in sequence." Everything starts with check_process_status — literally every turn. This tool takes the loan_request_id from session state, queries SQLite via ProcessStateService, and returns one of four actions: "proceed_to_analysis" for new applications, "resume" for partially completed ones with the list of completed steps, "return_status" for status checks, or "pending_approval" when we're waiting for HITL. The orchestrator's system prompt is structured to always call this first, and the before_tool callback enforces it. For a new application, the orchestrator loads the loan-orchestration-protocol skill via SkillToolset — this is a markdown file that gives the LLM the exact step-by-step workflow including when to pause for approval. Then it calls AgentTool(DocumentExtractionAgent). The before_model callback — inject_document_into_request — fires here. It checks session state for an "inline_document" key that was stored by the before_agent callback when the user's message contained base64-encoded content, and injects it as a Part in the LLM request. DocumentExtractionAgent has output_schema=LoanApplicationData — a Pydantic model with 13 fields: business_name, owner_name, ein, industry, years_in_business, annual_revenue, net_profit, loan_amount_requested, loan_term_months, collateral_offered, business_address, owner_email, owner_phone. The after_agent callback — after_agent_callback_with_state_logging — persists this to SQLite and checks for missing critical fields. If anything's missing, it sets a review issue and the process halts. Next, UnderwritingAgent. This agent has two tools. get_internal_business_data is a mock CRM that returns business registration data — the LLM uses it to cross-reference against the extracted application. retrieve_underwriting_context is the AutoRAG wrapper — and this is where it gets interesting. The LLM sees it as one tool call. But internally, in sub_agents/underwriting/rag_tools.py, it calls two separate functions: retrieve_eligibility_rules with the application profile (industry, years, revenue, loan amount, loan-to-revenue ratio) and retrieve_industry_guidance with the industry and NAICS code. Each makes an httpx POST to the OGX vector store endpoint — /v1/vector_stores/{id}/search — with max_num_results=3. The results are concatenated and returned as a single string to the LLM. The UnderwritingAgent returns an UnderwritingReport with eligibility_status (ELIGIBLE, INELIGIBLE, or REVIEW), matched_rule, risk_flags, and a recommendation. The branch point happens in the after_agent callback on UnderwritingAgent. If eligibility_status is INELIGIBLE, the callback does two things: it writes the PricingAgent step as "skipped" in SQLite, and it sets a session state flag. The before_tool callback on the orchestrator checks this flag and returns a skip message if the orchestrator tries to call PricingAgent. This is a belt-and-suspenders approach — the LLM prompt also tells the orchestrator to skip pricing for ineligible loans, but the callbacks enforce it programmatically. For eligible loans, PricingAgent runs calculate_loan_pricing — a deterministic function, not an LLM call. It takes the extracted application data and underwriting report, looks up the interest rate by risk tier from config (Tier 1: 6.50%, Tier 2: 7.75%, Tier 3: 9.25%, Tier 4: 11.00%), calculates monthly payment and total interest, and returns a PricingResult. Then the orchestrator stops — it presents the pricing to the user and asks for approval. This is genuine HITL: the conversation is suspended, the process status is set to "pending_approval" in SQLite, and nothing happens until the user explicitly says yes. For ineligible loans, the orchestrator loads the loan-adverse-action skill — ECOA requirements, decline letter template, tone guidance — and calls LoanDecisionAgent. Inside finalize_loan_decision, there's an automatic call to retrieve_regulatory_guidance that queries AutoRAG for ECOA and Reg B adverse action requirements, passing in the risk_flags from the UnderwritingReport. The LoanDecisionAgent LLM never sees this as a separate tool call — it receives the regulatory text as part of its context. The LLM-as-Judge fires after every orchestrator turn. It's a second litellm.acompletion call using the same model backend, with a structured prompt that receives the tool call sequence, all agent outputs as JSON, the user's message, and the orchestrator's response. It validates trajectory correctness (did tools fire in the right order?), grounding (do all numbers in the response match the structured outputs?), and completeness. The response_format is set to JudgeVerdict — a Pydantic model — so the judge's output is itself structured. If is_valid is false, the orchestrator's response is replaced with a generic error message. The verdict is also written to session state under _llm_judge_audit for debugging.

AutoRAG

Retrieval-augmented regulatory knowledge

How it works
  • OGX vector store with Milvus backend and nomic-embed-text-v1.5 embeddings
  • UnderwritingAgent calls retrieve_underwriting_context — one LLM tool call that internally makes 2 AutoRAG queries: eligibility rules + industry guidance
  • LoanDecisionAgent calls finalize_loan_decision — on the decline path, it internally calls retrieve_regulatory_guidance for ECOA adverse action requirements
  • Each query returns up to 3 chunks — focused retrieval, not a document dump
  • If AutoRAG is down, the agent falls back to a static eligibility_rules.json
The 9-document corpus
  • SBA general eligibility + DSCR requirements
  • Collateral requirements + LTV table
  • Prohibited business types (13 CFR § 120.110)
  • Adverse action notice rules (ECOA / Reg B)
  • Prohibited NAICS codes (30 codes)
  • Industry risk assessment guide
  • Risk tier + rate pricing guide
  • Applicant FAQ (20 Q&A)
  • Reapplication guidance
Let me go deeper on the RAG architecture, because there are some design decisions here that aren't obvious. The fundamental question was: where does regulatory knowledge live? We had three options. Fine-tuning — but regulations change and retraining is expensive. System prompt stuffing — but 78KB of regulatory text burns context window and dilutes the instruction. RAG — retrieve just the relevant chunks at decision time. We went with RAG, and specifically with RHOAI's AutoRAG service backed by OGX. The vector store uses Milvus with nomic-embed-text-v1.5 for embeddings. The corpus is 9 markdown documents totaling about 78KB of source material, seeded via tools/seed_autorag.py — a one-time script that reads the files from tools/corpus/, chunks them, and uploads to the OGX endpoint. The corpus covers three domains: eligibility (SBA general eligibility, DSCR, collateral requirements, LTV tables, prohibited business types under 13 CFR 120.110), regulatory (ECOA adverse action notice requirements under 12 CFR 1002.9, Regulation B), industry (prohibited NAICS codes — 30 of them — and an industry risk assessment guide), pricing (risk tier definitions and rate benchmarks), and FAQ/counseling (applicant FAQ and reapplication guidance). Now, the integration architecture. There are four retrieval functions defined in shared_libraries/rag_tools.py: retrieve_eligibility_rules, retrieve_industry_guidance, retrieve_regulatory_guidance, and retrieve_pricing_guidance. But here's what's important — not all of them are exposed as LLM-callable tools. retrieve_eligibility_rules and retrieve_industry_guidance are called internally by the retrieve_underwriting_context tool in sub_agents/underwriting/rag_tools.py. The LLM calls retrieve_underwriting_context with the application profile — industry, years in business, revenue, loan amount, NAICS code. Internally, that function calls both retrieval functions, concatenates the results, and returns a single combined string. From the LLM's perspective, it made one tool call. From the vector store's perspective, two separate queries ran with different query strings optimized for each retrieval task. The eligibility query is structured as "SBA 7(a) loan eligibility requirements for [industry] business with [years] years operating history, annual revenue [X], loan amount [Y]" — it's parameterized to the specific application. The industry query is "SBA eligibility ineligible industry [industry] NAICS code [code] risk tier classification prohibited business types." retrieve_regulatory_guidance is called internally by finalize_loan_decision in sub_agents/loan_decision/tools.py — but only on the ineligible path. When the UnderwritingReport has eligibility_status=INELIGIBLE, the tool automatically queries AutoRAG for ECOA and Reg B text, passing in the risk_flags from the underwriting output. The LoanDecisionAgent LLM never sees a separate RAG tool — it just gets richer context in its prompt. retrieve_pricing_guidance exists in the code but is currently unused — it's there for a future iteration where we might want to provide rate comparison context to PricingAgent. Each query hits the OGX endpoint at /v1/vector_stores/{vector_store_id}/search via httpx POST with max_num_results=3 and a 30-second timeout. The low max_num_results is intentional — we want focused, high-relevance chunks, not a document dump. Three chunks per query means the underwriting stage gets at most 6 chunks total (2 queries × 3 chunks), and the decline path gets at most 3 more. The fallback path is important. In the before_agent callback for UnderwritingAgent (before_agent_callback_with_state_check), there's logic that loads eligibility rules from a static JSON file — eligibility_rules.json — and stores them in session state. The LLM's system prompt references these rules. So if AutoRAG is completely unavailable — AUTORAG_BASE_URL not set, or the vector store unreachable — the agent still has a baseline set of eligibility rules to work with. It won't have industry-specific NAICS guidance or ECOA regulatory text, but it can still make an eligibility determination. The _search function in rag_tools.py handles this gracefully: if using_autorag() returns false, it returns an empty string; if the httpx call fails, it logs a warning and returns an empty string. No exceptions propagate to the agent.

Safety

Callbacks — guardrails at every lifecycle point

HookCallbackWhat it actually does
before_agent extract_request_id Parses the loan ID (SBL-YYYY-XXXXX) from the user message. No ID? Agent asks for one instead of guessing.
before_tool halt/skip guard Blocks tool execution if the process is halted, completed, or if pricing should be skipped for ineligible loans.
before_model inject_document Injects the loan application PDF or image into the LLM request context — only for DocumentExtractionAgent.
after_agent state_logging Persists every sub-agent's structured output to SQLite. Detects INELIGIBLE status and flags PricingAgent for skip.
after_agent llm_judge_gate A second LLM call that checks trajectory, grounding, and completeness. If it fails, the response is blocked.

The LLM-as-Judge validates every orchestrator response: Did the tools run in the right order? Do all numbers match the structured outputs? Is anything missing? If any check fails, the user sees a generic retry message — not a hallucinated answer.

ADK gives you four callback hooks on every LlmAgent, and we use all four. Let me walk through each one with the actual implementation details. before_agent — extract_request_id_from_request. This runs on the orchestrator at the start of every turn. It scans the user's message for a regex pattern matching the loan ID format — SBL-YYYY-XXXXX, where the prefix, year width, and sequence width are configurable in config.py. If it finds a match, it stores it in session state under "loan_request_id". It also checks for inline documents — base64-encoded PDF or image content in the message — and stores them under "inline_document" for later injection. This is the entry point for the entire workflow: no valid loan ID means the agent asks for one rather than proceeding with a hallucinated ID. before_tool — before_tool_callback_check_process_status. This is the orchestrator's gate. It runs before every tool call and checks multiple conditions. Is the process status "halted"? Block the tool and return a message asking for missing information. Is the process "completed"? Block the tool and return the completion status. Is the tool PricingAgent and has the underwriting callback set the skip flag for ineligible loans? Block the tool and return a skip message. This is belt-and-suspenders with the LLM prompt — the prompt tells the orchestrator to skip pricing for ineligible loans, but the callback enforces it programmatically. In a financial application, you don't rely on prompt compliance alone for control flow. before_model — inject_document_into_request. This only runs on DocumentExtractionAgent. When the callback fires, it checks session state for "inline_document", and if present, it modifies the LlmRequest to inject the document content as an additional Part. This is how the agent handles multimodal input — PDFs, images, and text documents are all handled through this single injection point. The key detail is that this happens at the model call level, not at the agent level — DocumentExtractionAgent's system prompt doesn't need to know how the document gets there. after_agent — two separate callbacks at two levels. On sub-agents, it's after_agent_callback_with_state_logging from shared_libraries/state_utils/state_callbacks.py. This does three things: (1) persists the sub-agent's structured output to SQLite via ProcessStateService, keyed by the agent name and the loan_request_id, (2) checks the output for issues — for example, if DocumentExtractionAgent returns data with missing critical fields, it creates a review issue and sets the process to "halted", (3) for UnderwritingAgent specifically, if eligibility_status is INELIGIBLE, it writes PricingAgent's step as "skipped" in SQLite and sets the session state skip flag. On the orchestrator, the after_agent callback is llm_judge_gate — the LLM-as-Judge. This is the most complex callback. It extracts the tool call sequence from the current invocation by iterating over session events filtered by invocation_id. It collects all agent outputs from session state — DocumentExtractionAgent_output, UnderwritingAgent_output, PricingAgent_output, LoanDecisionAgent_output — and serializes them to JSON, including Pydantic model_dump() for structured types. It builds a judge prompt from a template in after_agent_callback/prompt.py that includes the full tool sequence, all agent outputs as ground truth, the user's original message, and the orchestrator's final response text. The judge prompt is specific and detailed — it defines valid trajectory patterns (new eligible process, after approval, ineligible decline, status check, resume), invalid patterns (missing check_process_status, calling all four agents in one turn, LoanDecisionAgent without approval), and grounding rules (all numerical values must be traceable to agent outputs or the user's message, with explicit exceptions for status-check-only flows and partial flows). The response_format is set to JudgeVerdict — a Pydantic model with five fields: is_valid (bool), trajectory_correct (bool), grounded_in_context (bool), response_complete (bool), and reasoning (str). The judge call goes through litellm.acompletion using the same model backend as the agent — MaaS, Gemini API, or Vertex AI, determined by _build_judge_client_kwargs() which reads from the same config. If is_valid comes back false, the orchestrator's response is replaced with a generic error message and a reference ID. The verdict is also written to session state under _llm_judge_audit for observability. If the judge call itself fails — network error, model error, anything — the callback catches the exception, logs it, and returns a blocked response. We fail closed, not open. The user gets a retry message rather than an unvalidated response.

Resilience

Repair and resume — surviving failures

Dual-write: every sub-agent writes to both ADK session state and SQLite.

  • Pod restart? check_process_status reloads completed steps from SQLite
  • Missing data? Agent halts, asks the user, resumes from that step
  • User returns hours later? SQLite picks up where things left off
  • Approval in a new session? _load_step_data_from_db() loads prior outputs so the letter can be generated
State management in this system has three layers, and understanding why you need all three is important. Layer 1: ADK session state. This is in-memory, scoped to an InMemoryRunner session. When the orchestrator calls AgentTool(UnderwritingAgent), ADK runs the sub-agent and writes its structured output to session state under the agent's output_key — "UnderwritingAgent_output". Subsequent agents and callbacks read from these keys. The problem: InMemoryRunner stores sessions in a Python dict. If the pod restarts, everything is gone. And even without a restart, if the user's next message arrives on a different API session — which happens when Open WebUI starts a new request — the session state is empty. Layer 2: SQLite via ProcessStateService. This is the persistent layer. The SQLite database lives on a PVC at /app/data/ — configurable via STATE_DB_PATH env var. The schema tracks loan_request_id as the primary key, session_id, overall_status (active, pending_approval, completed, failed), current_step (which agent should run next), a steps JSON object with per-agent data (status, completed_at, data, error_message), and an issues array for missing fields or review flags. The after_agent callback writes to this on every sub-agent completion. The data field stores the full Pydantic model_dump() of the agent's output — so we have complete reconstruction capability. Layer 3: check_process_status — the bridge. This is a standalone tool function (not an agent), and it's always the first call in any turn. It takes the loan_request_id, queries ProcessStateService, and returns an action. For a new application: action="proceed_to_analysis". For a partially completed application: action="resume" with a list of completed steps — and critically, it writes all completed step data back into ADK session state. So if DocumentExtractionAgent and UnderwritingAgent completed before a pod restart, check_process_status reloads their outputs from SQLite into the fresh session, and the orchestrator sees them as if they'd just run. It then proceeds from the next uncompleted step. There's a fourth mechanism that handles a subtle edge case. When the user says "yes" to approve the pricing, that message might arrive in a completely fresh API session. check_process_status runs, sets action="proceed" or similar, and LoanDecisionAgent runs. But here's the problem: even though check_process_status reloaded the data into session state, if this is a fresh InMemoryRunner instance, the session state write might not have propagated correctly to the tool_context that LoanDecisionAgent sees. So finalize_loan_decision has a built-in fallback — _load_step_data_from_db(). It checks each prior agent's output key in tool_context.state, and if any of them are empty, it calls ProcessStateService directly to load the data. Three checks: DocumentExtractionAgent_output, UnderwritingAgent_output, PricingAgent_output. Each one falls back independently. The dual-write architecture means we never lose data. ADK session state is fast and convenient for within-turn access. SQLite is durable across restarts. check_process_status is the synchronization point. And _load_step_data_from_db is the last-resort fallback for edge cases where even the synchronization didn't fully propagate. One more detail: the overall_status transitions in SQLite are strict. active → pending_approval (after pricing, waiting for HITL) → completed (after loan decision) or failed (on unrecoverable error). The process can also go active → failed if a critical step fails. These transitions are enforced in ProcessStateService methods — you can't go backwards, and you can't skip states.

Platform

What this looks like on OpenShift AI

Model Serving (MaaS)

Gemini 2.5 Flash via OpenAI-compatible endpoint through LiteLLM. Switch to Vertex AI or direct API key by changing env vars — no code changes.

AutoRAG (OGX)

9-doc regulatory corpus in Milvus + nomic-embed-text-v1.5. Queried 3 times per loan: 2 at underwriting, 1 at loan decision.

MLflow Tracing

Optional — set MLFLOW_TRACKING_URI and every LLM call auto-logs as spans. Degrades gracefully if unavailable.

Let me walk through each RHOAI capability and how it actually integrates at the code level. Model Serving — MaaS. The model factory is in gemini_custom.py. There's a get_model() function that checks config.using_maas() — which is just bool(MAAS_BASE_URL and MAAS_API_KEY). If true, it returns a MaaSLiteLlm instance from the rh-maas-litellm package — this is a custom ADK model class that wraps LiteLLM with MaaS-specific configuration: the base URL, API key, URL path template (default: /gemini-external/{model}/v1), and SSL verification settings. The URL path is templated — {model} gets replaced with the model name at call time, so the same endpoint can serve multiple models. If MaaS isn't configured, it falls back to GeminiPreview — a subclass of ADK's native Gemini class that supports both GOOGLE_API_KEY (direct API) and GCP Application Default Credentials (Vertex AI). The beauty of this is that all five LlmAgent instances and the LLM-as-Judge callback use the same model factory. Change MAAS_BASE_URL in the ConfigMap and the entire system switches backends without a code change. There's a subtle technical detail worth mentioning: MaaS returns gzip+chunked transfer encoding, which triggers an httpcore read-stall bug. In gemini_custom.py, we force "Accept-Encoding: identity" on all LiteLLM requests to work around this. This is the kind of production issue that only shows up when you're running through a gateway, not when you're hitting the Gemini API directly. AutoRAG — OGX. I covered the retrieval architecture in detail on the previous slide, but from a platform perspective: the agent connects to AutoRAG via two env vars — AUTORAG_BASE_URL and AUTORAG_VECTOR_STORE_ID. The API is simple: POST to /v1/vector_stores/{id}/search with a JSON body containing the query string and max_num_results. The response is an array of chunks with content text. All calls go through httpx with a 30-second timeout and configurable SSL verification (AUTORAG_SSL_VERIFY). The vector store was provisioned through RHOAI's AutoRAG service, and the corpus was seeded using tools/seed_autorag.py which reads from tools/corpus/ — 9 markdown files organized by domain (eligibility, regulatory, industry, pricing, faq). MLflow Tracing. The integration is in tracing.py. On server startup, the FastAPI lifespan handler calls enable_tracing(). This function checks for MLFLOW_TRACKING_URI in the environment — if it's not set, tracing is silently skipped and the agent starts normally. If it is set, the function does a health check — it pings {tracking_uri}/health with a configurable timeout (MLFLOW_HEALTH_CHECK_TIMEOUT, default 5 seconds) and retry interval. If the health check passes, it calls mlflow.set_tracking_uri(), mlflow.set_experiment() with a configurable experiment name (default: "small-business-loan-agent"), enables async logging via mlflow.config.enable_async_logging(), and then calls mlflow.litellm.autolog(). That last call is the key — it monkey-patches LiteLLM so every completion call automatically generates an MLflow span with the prompt, response, latency, token counts, and model metadata. Since both the agent's LLM calls and the LLM-as-Judge go through LiteLLM, you get full observability across the entire pipeline. If the MLflow server becomes unreachable after startup, the async logging just fails silently — it doesn't crash the agent. And there's a wrap_func_with_mlflow_trace utility that lets you add custom spans to non-LLM functions — tool calls, RAG queries — though we're not using that extensively yet. OpenShift AI Deployment. The Containerfile builds a standard Python image with the FastAPI server. The server exposes three endpoints: /chat/completions and /v1/chat/completions (OpenAI-compatible), /health for readiness probes, and /.well-known/agent-card.json for A2A agent discovery. The pod runs with an OpenShell init container that configures network isolation — the agent can only reach the MaaS gateway and the AutoRAG endpoint. ConfigMap holds operator-tunable parameters: MODEL_NAME, MAAS_BASE_URL, AUTORAG_BASE_URL, AUTORAG_VECTOR_STORE_ID, BANK_NAME, the four interest rate tier values (RATE_TIER_1 through RATE_TIER_4), DEFAULT_LOAN_TERM_MONTHS, and INSURANCE_VERIFICATION_DAYS. SealedSecrets hold MAAS_API_KEY and the OpenShell TLS certificates. PVC at /app/data/ provides durable storage for the SQLite state database. One thing to note: EvalHub integration is not in this version. The agent uses ADK's built-in adk eval for smoke tests — there are integration tests in tests/integration/test_agent.py that run the full pipeline — and the LLM-as-Judge serves as a runtime quality gate. But we haven't yet connected to RHOAI's EvalHub for systematic evaluation datasets and scoring. That's on the roadmap.

Knowledge

Skills — domain knowledge loaded on demand

The orchestrator loads markdown files as "skills" using ADK's SkillToolset. These aren't hard-coded into prompts — the LLM decides when to load them based on context.

SkillWhen it's loadedWhat it contains
loan-orchestration-protocol Start of every new application Step-by-step HITL workflow: extract → underwrite → price → approve/decline
loan-eligibility-guide When explaining eligibility decisions 5 SBA eligibility rules, risk flags, status definitions
loan-pricing-guide After PricingAgent returns Risk tier table (Tier 1–4), rate ranges, how to present pricing to the user
loan-adverse-action Before generating a decline letter ECOA requirements, decline letter template, tone and compliance guidance

Only the orchestrator has access to skills. Sub-agents are locked down: disallow_transfer_to_parent=True, disallow_transfer_to_peers=True. They can't load skills, can't call other agents, can't transfer control.

There's an important distinction between skills and RAG in this architecture, and it's worth understanding why we use both. Skills are workflow knowledge — they tell the LLM how to behave. The orchestration protocol skill defines the exact step-by-step workflow: always call check_process_status first, load the protocol, run agents in order, present pricing and pause for approval, handle the three paths (eligible, ineligible, repair). The eligibility guide has the five SBA eligibility rules with specific thresholds. The pricing guide has the risk tier table — Tier 1 through 4 with rate ranges — and a template for how to present pricing to a user including what information to include and how to ask for approval. The adverse-action skill has ECOA requirements for decline letters — specific elements that must be included, tone guidance, and a letter template. RAG is reference knowledge — it provides factual grounding for specific decisions. When the underwriting agent needs to know whether a cannabis business is SBA-eligible, it doesn't rely on the LLM's training data or the skill content — it queries AutoRAG for the actual 13 CFR 120.110 text and the prohibited NAICS codes list. When LoanDecisionAgent generates a decline letter, it queries for the actual ECOA adverse action requirements — specific reason codes, required notice elements, timing rules under 12 CFR 1002.9. The loading mechanism: skills are stored as markdown files in a /skills directory at the repo root — one subdirectory per skill, each containing a SKILL.md. In agent.py, load_skills_from_dir reads the directory and creates skill objects. SkillToolset wraps them and provides three tools to the LLM: list_skills (returns available skill names and descriptions), load_skill (loads a skill's content into the conversation), and load_skill_resource (loads a specific resource from a skill). The SkillToolset is listed first in the orchestrator's tools array — skills first, then check_process_status, then the four AgentTool wrappers. This ordering is intentional: it encourages the LLM to discover domain knowledge before taking action. The LLM decides when to load skills based on context. The orchestration protocol skill says in its content "load this skill at the start of every new loan application." The pricing guide is referenced in the orchestrator's system prompt as something to load after pricing results are available. The adverse-action skill is loaded when the orchestrator needs to handle a decline. These aren't hard-coded trigger conditions — the LLM reads the skill descriptions and decides based on the conversation context. The access control is strict. Only the orchestrator has SkillToolset in its tools list. Sub-agents cannot load skills, cannot discover skills, cannot call other agents. In each sub-agent definition — document_extraction_agent, underwriting_agent, pricing_agent, loan_decision_agent — both disallow_transfer_to_parent and disallow_transfer_to_peers are set to True. This prevents any autonomous control transfer. A sub-agent processes its input, produces structured output via its output_schema, and returns. The orchestrator decides what happens next. The skills are baked into the container image at /app/skills/. Updating a skill means updating the markdown file, rebuilding the image, and redeploying — ArgoCD syncs. This is intentionally different from the RAG corpus, which can be updated by re-running seed_autorag.py without a code change. Skills change the agent's behavior (workflow, formatting, decision logic). RAG content changes the factual basis for decisions. They evolve at different rates and should be managed separately.

Let me wrap up with the key architectural takeaways — things you'd want to carry into your own agent implementations. First, the multi-agent pattern works when the problem has genuinely distinct reasoning stages. Document extraction, underwriting, pricing, and letter generation require different prompts, different tools, and different output schemas. The AgentTool pattern in ADK makes this clean — sub-agents are tools to the orchestrator, with full isolation of prompts, tools, and state writes. The alternative — one big agent with all tools — produces unpredictable tool selection and cross-stage contamination. Second, callbacks are your policy enforcement layer, and you should use all four hooks. before_agent for input validation and context setup. before_tool for gating and access control. before_model for request modification (document injection, prompt augmentation). after_agent for state persistence, issue detection, and quality validation. The key principle: don't rely on prompt compliance alone for control flow in a financial application. The LLM prompt says "skip pricing for ineligible loans." The before_tool callback enforces it programmatically. Belt and suspenders. Third, the LLM-as-Judge pattern adds latency — it's a second LLM call on every turn — but for domains where correctness matters more than speed, it's worth it. The judge checks trajectory (did the right tools fire in the right order), grounding (do all values in the response match the structured outputs), and completeness (is anything missing). It returns structured output via Pydantic, so you get machine-readable audit trails. And it fails closed — if the judge call itself fails, the response is blocked, not passed through. Fourth, state persistence needs to be multi-layered. ADK session state for within-turn access. Persistent storage (SQLite on PVC in our case) for cross-turn and cross-restart durability. A synchronization mechanism (check_process_status) to bridge the two. And a last-resort fallback (_load_step_data_from_db) for edge cases where synchronization didn't fully propagate. This is more complexity than a simple chatbot needs, but for a multi-turn workflow with HITL approval gates, you need it. Fifth, the RHOAI platform capabilities — MaaS, AutoRAG, MLflow — aren't bolted on as demos. They're structural. MaaS provides the LLM backend for all five agents and the judge. AutoRAG provides regulatory grounding that would be impractical to maintain in system prompts. MLflow provides the observability you need to debug a multi-agent pipeline where a single user turn can generate six LLM calls across five agents plus a judge. And the deployment model — container, PVC, ConfigMap, SealedSecrets, OpenShell — is standard OpenShift AI operational practice.
